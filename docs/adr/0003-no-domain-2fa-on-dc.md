# ADR 0003: TOTP-двухфакторная аутентификация по SSH — только на server-b, не на контроллере домена

## Статус
Принято

## Контекст
Стенд получил рабочий SSH-доступ доменных пользователей через SSSD (см. фиксы
базового доступа в CHANGELOG от 2026-09-21). Следующим шагом было решено
добавить второй фактор (TOTP через PAM, `libpam-google-authenticator`) для
входа по SSH — сначала на обоих хостах, `server-a` (контроллер домена) и
`server-b` (SSSD-клиент, рабочий узел с микросервисами).

При попытке завести TOTP-секрет для пользователя `administrator` на
`server-a` выяснилось, что доменные пользователи там вообще не резолвятся
как POSIX-аккаунты: `/etc/nsswitch.conf` на `server-a` содержит только
`passwd: files systemd`, без `sss` — в отличие от `server-b`. Это ожидаемо:
`server-a` — сам контроллер домена, и роль `samba_ad` не разворачивала на
нём `winbind`/`idmap`, которые нужны, чтобы Samba AD DC мог сам резолвить
доменные учётки в локальные Unix-идентификаторы для входа через PAM.

Есть и более фундаментальная причина не входить на DC доменными учётками:
циклическая зависимость. Если вход на контроллер домена возможен только
через сам домен (Kerberos/LDAP к этому же серверу), а служба AD на нём
почему-то не работает — администратор не сможет зайти и на сам сервер,
чтобы её починить. Поэтому на практике контроллеры домена обычно
администрируются через локальные (не доменные) учётные записи, а не через
Kerberos/LDAP к самим себе.

## Решение
Реализовать TOTP-2FA по SSH (PAM + `pam_google_authenticator`,
`KbdInteractiveAuthentication`) только для `server-b`, оформив это отдельной
Ansible-ролью `mfa`, применяемой к группе `domain_clients` (сейчас — только
`server-b`). На `server-a` изменения полностью откачены до исходного
состояния; администрирование `server-a` продолжает идти как и раньше —
через `docker exec` (то есть через доверие к самому Mac-хосту), а не через
SSH с доменным логином.

Сам секрет TOTP (`~/.google_authenticator`) осознанно не автоматизирован
через Ansible — это личный секрет конкретного пользователя на конкретном
хосте, а не часть инфраструктурной конфигурации, и генерируется вручную
командой `google-authenticator`.

## Последствия
- Позитивное: устранена циклическая зависимость «нужен AD, чтобы зайти на
  сервер, который поднимает AD» — контроллер домена остаётся управляемым
  даже при проблемах с самим доменом.
- Позитивное: меньше поверхность изменений — не нужно разворачивать и
  поддерживать `winbind`/`idmap` только ради тестового логина.
- Компромисс: у `server-a` сейчас нет второго фактора вообще ни для какого
  способа входа — реальная граница доверия сейчас смещена на уровень
  доступа к самому Mac и его Docker-сокету (`docker exec`), а не на PAM.
  Если в будущем понадобится полноценный SSH-доступ к `server-a` (не через
  `docker exec`), эту границу нужно будет пересмотреть отдельно.

## Рассмотренные альтернативы
1. **Развернуть `winbind` + `idmap` на `server-a`**, чтобы доменные
   пользователи резолвились и там так же, как на `server-b` через SSSD.
   Отклонено на данном этапе: добавляет отдельный, ранее не использованный
   в проекте механизм (`winbind` вместо `sssd`) ради сценария, который
   сам по себе спорен с точки зрения безопасности (см. контекст).
2. **TOTP для локальной (не доменной) администраторской учётки на
   server-a** — создать отдельного локального пользователя специально для
   аварийного доступа, защищённого TOTP, не завязанного на домен. Отложено
   на будущее: решает проблему циклической зависимости, но требует
   дополнительной проработки (отдельный процесс восстановления доступа,
   отдельное хранение секрета) и не является насущной необходимостью, пока
   `docker exec` полностью покрывает потребности администрирования.
3. **Не делать 2FA на server-a вообще, ограничиться server-b** — выбрано.
   Обоснование: `docker exec` с хоста уже требует физического/логического
   доступа к Mac, что для тестового стенда является приемлемой границей
   доверия; усложнять контроллер домена ради сценария, который в проде не
   рекомендуется, не оправдано.
