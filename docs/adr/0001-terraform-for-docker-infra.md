# 0001. Управление Docker-инфраструктурой через Terraform вместо ручного docker-compose

## Статус
Принято — 2026-09-07

## Контекст
"Внешняя" инфраструктура стенда — два Ubuntu-контейнера (`server-a`, `server-b`), имитирующие сервера, и две bridge-сети — описана в `~/it-infra-lab/docker-compose.yml` на Mac и запускалась вручную командой `docker-compose up`.

У этого подхода несколько проблем:
- Файл не проверяется никаким dry-run — нет способа узнать, совпадает ли реально работающая инфраструктура с тем, что в нём описано.
- Нет воспроизводимого, версионируемого процесса пересоздания стенда.
- Контейнеры содержат недели ручной настройки (база Samba AD, ключи и конфиг WireGuard, состояние вложенного Docker) — эти данные лежат в перезаписываемом слое контейнера, а НЕ в примонтированном `/root`. Уничтожение и пересоздание контейнера означает полную потерю этих данных.

Цель по повышению "зрелости" стенда — сделать его декларативным и переразвёртываемым в несколько команд, не трогая то, что уже работает.

## Решение
- Завести Terraform с провайдером `kreuzwerker/docker` в каталоге `terraform/` этого репозитория.
- Описать существующие `docker_network` (net_a, net_b) и `docker_container` (server-a, server-b) в HCL так, чтобы они точно соответствовали текущему `docker-compose.yml`.
- Взять существующие сети и контейнеры под управление Terraform через `terraform import`, вместо того чтобы уничтожать и создавать их заново.
- Считать `terraform plan` с нулём разрушительных изменений (`0 to destroy`) обязательным условием перед любым `apply` — по аналогии с уже применяемой практикой `ansible --check --diff` для Ansible-ролей.

## Последствия

Положительные:
- Топология внешней инфраструктуры теперь версионируется, проверяема и воспроизводима через `terraform apply`, а не ручной `docker-compose up`.
- `terraform plan` даёт повторяемый инструмент обнаружения дрейфа конфигурации.

Отрицательные / известные ограничения:
- `terraform import` в версии провайдера `kreuzwerker/docker` (~> 3.0) не подтягивает в state несколько атрибутов `docker_container`, помеченных как требующие пересоздания при изменении (`env`, `networks_advanced`, `volumes`). Из-за этого первый `plan` после импорта контейнера с такими полями в конфиге показывает полное пересоздание. Это было один раз безопасно исправлено вручную — через `terraform state pull` / `terraform state push` — подставив в state те же значения, что уже реально существуют (проверено через `docker inspect`), без единого реального обращения к Docker. Любой следующий импортируемый контейнер потребует той же процедуры.
- Ресурс `docker_image` в этой версии провайдера вообще не поддерживает `terraform import` — образ указывается напрямую строкой (`"ubuntu:22.04"`), без отдельного управляемого ресурса.
- `~/it-infra-lab/docker-compose.yml` на Mac теперь устаревший справочный файл — источником правды по топологии сетей и контейнеров стал `terraform/main.tf`.

## Рассмотренные альтернативы
- Уничтожить и создать контейнеры заново через Terraform "с нуля" — отклонено: это уничтожило бы недели ручной настройки AD/WireGuard/вложенного Docker, которая не находится в примонтированном `/root`.
- Оставить ручной `docker-compose` — отклонено: не соответствует цели "воспроизводимо в 3-4 команды, версионируемо, проверяемо на дрейф".
